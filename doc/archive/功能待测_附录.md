## A. TF 卡素材与实测参数

卡：F:，**FAT32**，3.65 GB（可用 3.57 GB）。根目录内容：

| 文件名 | 大小 | 实测参数 | 用途 |
|---|---|---|---|
| `PIC1.bmp` | 921,654 | 640×480 / 24bit / 无压缩 | 基准图，不缩放 |
| `PIC2.bmp` | 921,654 | 640×480 / 24bit / 无压缩 | 与 PIC1 内容不同，可看出切换 |
| `PIC3.bmp` | 180,054 | **200×300** / 24bit / 无压缩 | 小图 → 验等比放大 + 黑边 |
| `PIC4.bmp` | 2,880,054 | **1200×800** / 24bit / 无压缩 | 大图 → 验等比缩小 |
| `TRACK01.RAW` | 26,717,624 | **278.31 秒**（4:38），偶数 | 周杰伦《霍元甲》 |
| `TRACK02.RAW` | 21,720,000 | **226.25 秒**（3:46），偶数 | 大张伟《阳光彩虹小白马》 |
| `TRACK03.RAW` | 980,534 | **10.21 秒**，偶数 | 奶龙大笑音效，便于快速验证切歌 |

四张图 MD5 互不相同，切换时能明显看出区别；尺寸恰好覆盖"原尺寸 / 放大 / 缩小"三种缩放路径。

### 实测结论（与文档口径的差异）

1. **文件名小写 `.bmp` 能被识别**。FAT32 目录项的 8.3 短名固定按大写存储（大小写只体现在 NTRes 标志位），扫描器比对的是原始大写字节 `PIC` + `BMP`，所以小写显示名照样匹配。`使用说明 §2.3` 说"文件名必须大写"偏严，不必改名。
2. **三首曲目都是响度拉满的成品**，采样峰值触及 ±32768 满幅。`audio_volume_gain.v` 最大档 `vol=15 → gain_q15=32760`（0.99976×），增益**从不超过 1.0**，满幅输入不会被推爆削波。默认档 12（0.80×）时峰值约 26,200，余量充足。
3. **`System Volume Information` 不干扰扫描**。扫描器要求目录项属性字节**严格等于 `0x20`**（归档位），目录的 `0x10`、长名项的 `0x0F` 都不匹配，会被跳过。
4. **属性必须恰好 `0x20`**：若图片被设成只读（`0x21`）会读不到。正常拷贝进卡的图片不受影响。
5. **旧 `MUSIC.WAV` 已删除**（27.5 MB，`TRACK01` 的字节级副本；扫描器虽输出 `music_valid`，但该信号在 `sd_card_bmp.v` 中只声明连线、无下游消费者，属悬空）。

## B. 曲目播放逻辑（2026/10/20 逐行核对代码）

以下结论来自 RTL 源码，不是文档转述。

### B1. 首数怎么定

- 扫描器只认 `TRACK01.RAW`~`TRACK16.RAW` 这 16 个名字（`fat32_volume_scanner.v:333-334`：`TRACK0`+`1~9` 或 `TRACK1`+`0~6`）。
- 每个名字占一个槽，`track_list.v:95-98` 置 `valid_mask[index]`，`track_count` **只在首次出现时 +1**——同号文件重复出现只覆盖内容，不重复计数。
- `valid_mask` 是 16 位、`track_list` 是 16 槽（每槽 19 字节，共 1 块 BRAM9K），所以**上限 16 首**。
- **卡里放几首就播几首**（0~16 皆合法），16 是命名容量上限、不是测试要求。

### B2. 顺序与循环

- 起始曲目 = `first_valid(valid_mask)`，即**编号最小那首**。
- 播完自动下一首：`next_valid` 逐个往上找下一个置位槽（`track_controller.v:50-71`），4 位索引自然回绕 → **最后一首播完回到最小那首**，无限循环。
- 顺序只由编号决定，**与卡上存放顺序、拷贝顺序无关**。
- 缺号会被跳过：逐位扫描而非简单 +1，缺 02 时 01 播完直接到 03。

### B3. 什么文件算数（四项全满足，`fat32_volume_scanner.v:354-357`）

1. 名字严格 `TRACK01`~`TRACK16` + 扩展名 `RAW`；
2. 目录项属性字节**恰好 `0x20`**；
3. 起始簇号 ≥ 2；
4. 文件大小**非 0 且为偶数**（奇数长度直接忽略，16bit 采样必须对齐）。

### B4. 音源切换时机（反直觉，重要）

- `track_controller.enable = all_resident && scan_done`（`sd_card_bmp.v:892`）。
- `all_resident` 要等**所有找到的图片都装载完**才置 1（`sd_card_bmp.v:752-754`）。
- 所以**上电是：先响测试音 → 图片装载完成后才切成音乐**。测试音那段是设计使然，不是故障（对应主表 P0-02）。
- 音源选择看 `playlist_active`：置 1 播 WAV，为 0 播测试音（`top_tf_hdmi_audio.v:963-964`）。曲目切换期间 `playlist_active` 保持 1，**不会中途跌回测试音**。

### B5. 坏曲处理

- `wav_play_error` 时置 `failed_mask[current_index]`，重新选下一首（`track_controller.v:221-225`）。
- 有效集合 = `valid_mask & ~failed_mask`，坏曲本次上电期间永久跳过。
- **边界缺陷（已记录，本阶段不修）**：若所有曲目都失败，`available_mask` 归零 → 回 `C_EMPTY`，而 `C_EMPTY` 判断用的是 `valid_mask`（未排除 failed），会从头重试第一首，形成"重试—失败—再重试"循环。

### B6. 长按参数

`key_longshort #(.CLOCK_MHZ(25), .LONG_CYCLES(15_000_000), .REPEAT_CYCLES(3_000_000))`（`top_tf_hdmi_audio.v:971-975`）：

- 长按判定 = 15,000,000 / 25MHz = **正好 600 ms**；
- 连发间隔 = 3,000,000 / 25MHz = **120 ms**；
- 仅在音量模式有效（`vol_mode_v` 门控），切图模式长按不切歌。

### B7. 扫描完成与报错

- 扫描器**不在找齐 4 张图时提前退出**，而是扫到根目录末尾（跟随根目录簇链），确保图片后面的曲目也能被找到（`fat32_volume_scanner.v:492`）。
- 扫描结束一定置 `scan_done`，但若图片不足 4 张会同时置 `fs_error = 0x22`（`ERR_RESOURCE_MISSING`）。**图片不全只标记错误，不阻止音乐播放**——音乐依赖 `all_resident`（所有找到的图装载完）。

## C. 曲目转换工具

`Project/src/user_source/hdl_source/python/wav_to_track_raw.py`

| 项 | 结论 |
|---|---|
| 转码参数 | `-ac 1 -ar 48000 -c:a pcm_s16le -f s16le`，与固件要求完全一致 |
| 端到端验证 | 44.1kHz 立体声 WAV → 1,163,266 字节 / 12.12 秒；同参数转 `Test.m4a` 得 1,163,264 字节，与原 `TRACK02.RAW` 字节数相同 |
| MP3 实测 | 三首 MP3（44.1kHz 立体声）均转换成功，时长与源一致、字节数均为偶数 |
| 防护逻辑 | 拒绝覆盖已有文件、拒绝非法输出名、拒绝空或奇数长度输出 |
| ffmpeg | 已把 `D:\Format\FormatFactory`（ffmpeg **7.1**）加入用户 PATH；**需新开终端或重启 DSH 后生效** |

**输入格式限制已放宽（2026/10/20）**：原脚本第 15 行硬性要求 `.wav`，导致 MP3/FLAC/M4A 无法转换。现改为只校验文件存在，转码逻辑、输出名校验、防覆盖逻辑均未改动。

```powershell
# 新终端直接运行（PATH 已含 ffmpeg）
python Project/src/user_source/hdl_source/python/wav_to_track_raw.py "新歌.mp3" TRACK01.RAW
```

> 当前 DSH 会话未继承新 PATH，本会话内转换需先 `$env:PATH = "D:\Format\FormatFactory;" + $env:PATH`。

> **凑满 16 首不必转码**：扫描器只校验文件名、簇号与大小（偶数），不看内容，把 `TRACK01.RAW` 复制成 `TRACK04`~`TRACK16.RAW` 即可。
