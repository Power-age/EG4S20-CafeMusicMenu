### 结论

1. **瓶颈不是 LUT 数量，而是打包效率**：LUT 只用 81.75%，slices 却已 92.63%；「仅寄存器」单元 1477、「LUT+REG 合并」7933，说明大量单元因布线/控制集分散而无法紧凑打包。
2. **没有明显死逻辑**：各模块都在使用中（`u_scanner` 仅启动扫描但功能必需）。
3. **真正可回收的大项都是结构性重构**，不适合放在阶段 0 的半天窗口：

| 候选 | 潜在收益 | 代价 | 判断 |
|---|---|---|---|
| 两个 `fat32_chain_reader` 合并为一个分时复用 | ~1100 LE | 图片与音频会同时占用链路，可能卡音频 | **不做**，风险高 |
| `volume_scanner` 复用 `u_chain` 做目录枚举 | ~1700 LE | 扫描与簇读取语义不同，需重写 | **不做** |
| 多个 `key_press_debounce` 实例合并（现 5 个：51+55+59+128+128） | ~150~200 LE | 时序冲突、需重新验证按键 | **暂不做**，留作后备 |
| `color_bar`／测试音等调试逻辑 | <150 LE | — | **暂不做**（调试需要） |

4. **阶段 0 的结论：不重构，靠"控制新增量"过门禁。** LUT 预算还剩约 3500（到 100%），slices 预算到 94% 只剩约 130 个。**设置界面新增逻辑必须控制在 300~400 LE 以内**，超出就启用上表的后备项。

## 0-2 OSD Buffer 扩容 256×16 → 256×80

### 为什么必须扩容

| 项 | 现值 | 需求 |
|---|---|---|
| `osd_buffer` | 256 列 × **16 行** × 2bit = 4096 | 面板 8 行文字 × 8 buffer 行 = **64 行**，加状态栏 8 行 → **80 行** |
| 字体 | 8×8 点阵 | 1 字符 = 8×8 buffer 像素 = 16×16 屏幕像素 |
| 屏幕映射 | 1 buffer 像素 = **2×2** 屏幕像素 | 80 行覆盖 160 屏幕行，正好容纳 ~136~160px 高的面板 |

### 存储实现

- 每块 `EG_LOGIC_BRAM` 保持 **4096×2bit（1 块 BRAM9K）** 不变；
- 扩为 **5 块**，用行高位选块：`bank = y[6:4]`（0~4）、`offset = {y[3:0], x[7:0]}`（12 位，与现址完全一致）；
- 读数据选块需与 BRAM 一拍延迟对齐（`rd_y` 的 bank 位打一拍）；
- BRAM 36 → **40**，与 §4.0 一致。

### 改动文件（5 个）

| 文件 | 改动 |
|---|---|
| `osd_buffer.v` | `wr_y`/`rd_y` 4→7 位；5 块 BRAM + 块选择；SIM 模型数组 4096→20480 |
| `osd_renderer.v` | `req_y` 4→7 位；`buf_wr_y` 4→7 位；`dirty[15:0]` → `dirty[79:0]`；`clr_cnt` 12→15 位（清屏扫描 4096→20480） |
| `status_bar_render.v` | `req_y` 4→7 位（输出行号改为 72 起的绝对行） |
| `osd_buffer_overlay.v` | `rd_y` 4→7 位；状态栏文字读起始行由 `8` 改为 `72`；预留面板区（暂不渲染，0~63 行空置） |
| `top_tf_hdmi_audio.v` | 相应 wire 位宽；`osd_dirty_row` 16→80 位 |

### 验收（本步不改视觉）

- `vlog` 全量编译无新错误
- 顶层 `syn_1` 通过，**BRAM = 40**
- 上板：底部状态栏五字段显示与 E16 **完全一致**（内容、位置、字号不变）
- slices 不超过 94%

### 不做的事（留给 V2-10）

- 面板背景/圆角/边框几何
- 面板文字布局与菜单项
- 面板显隐控制

## 0-3 输入事件预处理

### 目标

把按键原始电平统一转换成语义事件，供 `menu_controller`（V2-12）直接消费，避免状态机里混入去抖与长短按判断。

### 现有资源

| 模块 | 用途 |
|---|---|
| `key_longshort`（`u_key1_longshort`、`u_key2_longshort`） | 已产出短按/长按，`REPEAT_ENABLE=0`（一次长按只触发一次） |
| `key_press_debounce`（多处） | 去抖 |

### 需新增

- **双击检测**：同一按键 300ms 内两次短按 → 双击事件；单击事件**延迟 250ms** 输出（等待是否会变成双击）
- 输出统一为：`press_short`、`press_long`、`press_double` 三路脉冲（每键一份）

### 验收

- 新增 `sim/tb_key_events.v`，覆盖：单击（250ms 后出事件）、双击（只出双击、不出单击）、长按（只出长按）、连按抖动
- 上板：状态栏/切图行为与 E16 一致（此时事件尚未接入，仅内部产生）

## 回退点与风险

| 项 | 说明 |
|---|---|
| 回退点 | E16（`MD5 ECD201E5`，已上板验证） |
| 主要风险 | `osd_renderer` 的 `dirty[79:0]` 与 `clr_cnt` 加宽会小幅增加面积；清屏扫描从 4096 拍变 20480 拍（消隐期内完成，需确认仍在 VS 消隐窗口内） |
| 面积风险 | 若 slices 超 94%，先启用 0-1 表里的后备项（合并去抖/删调试逻辑） |
| 验证顺序 | 每改一个文件先 `vlog` 全量编译 → 全部改完再 `syn_1`+`phy_1` → 上板确认状态栏无变化 |

### 记录 4：冷上电黑边异常——概率性上电竞态（2026/10/21 13:05）

**现象**：用户刷 `MD5 19476320`（OSD 扩容版）后冷上电，黑边不是纯黑；KEY1 软复位后恢复正常。**重新烧录同一 RTL 的另一份 bitstream（`FE58458E`）后，冷上电正常。**

**判定**：同一份 RTL 时好时坏 → **概率性上电竞态，不是确定性逻辑缺陷**。与 10/20 修掉的 PLL 锁问题是同一类（当时把 `rst_all` 纳入三个 PLL 的 lock），但在当前网表下该修复仍不足以百分百覆盖。

**已排除的假设**

| 假设 | 证据 |
|---|---|
| 清屏被跳过 | 清屏 FSM 完全握手（等 `wr_ack_sync`、写满 307200 才进下一 bank），且等 `sd_init_done`（约百毫秒）后才启动，四个 bank 全清 |
| 复位恢复/撤销时序违例 | TD 报告中 removal 检查余量 +0.253ns，`rst_all` 无违例路径 |

**已试但否决的方案：上电复位计数器（POR）**

在 `clk`（50MHz 输入时钟）上计数，三个 PLL 全锁后再等 2.6ms 才释放 `rst_all`。**结果：seed 3 直接路由失败（`u_scanner` 局部拥塞，`PHY-8023`）；seed 1 构建成功但 WNS 恶化到 −4718ps**。说明当前设计已到资源刀尖，增加 17 个寄存器就会掀翻布局。**已完整回退**。

**结论**：暂不处理，登记为已知概率性问题；若在最终验收或演示时复现，再考虑成本更低的方案（例如只给视频输出通路加一个小状态机置黑，而不是动全局复位）。**当前构建（`FE58458E`）冷上电正常。**

**顺带的重要教训（已影响流程）**：TD 批处理**路由失败时仍返回 exit 0**，且不更新 `route.qor` / bitstream。判断构建成功必须同时满足：
1. 日志中无 `PHY-8023` / `RUN-8102` / `Routing violations`；
2. bitstream 时间戳**晚于**本次构建开始时间。
只看 `route.qor` 会读到上一次的旧数字（本次差点据此误判）。
### 记录 5：0-3 输入事件预处理完成（2026/10/21 13:4x）

**新增文件**

| 文件 | 说明 |
|---|---|
| `hdl_source/key_events.v` | 按键事件预处理：内部复用 `key_longshort`（不重复去抖逻辑），额外产出 `single_pulse`（延迟单击）与 `double_pulse`（双击） |
| `sim/tb_key_events.v` | 4 场景单元测试：单击 / 双击 / 长按 / 抖动 |

**参数**：`CLOCK_MHZ`（25）、`DEBOUNCE_MS`（20）、`LONG_MS`（600）、`DOUBLE_MS`（300）。

**设计要点与踩到的坑**

1. `short_pulse` 不是单拍脉冲且**在松手时产生**，最初按电平采样导致每拍刷新时间戳、`single_pulse` 永远不出。改为**取上升沿**后正常。
2. 因为事件在松手时产生，双击窗口量的是「松手→松手」= 间隔 + 按键时长。实测参数下（按 100ms、间隔 100ms）远小于 300ms 窗口，实用无问题；但单测参数必须留足余量，故单测用 `DOUBLE_MS=6`。
3. 单击延迟取与双击窗口相同的 300ms（规格写 250ms 是下限），保证不会既出单击又出双击。
